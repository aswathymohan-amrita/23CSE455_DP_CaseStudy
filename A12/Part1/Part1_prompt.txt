==================================================================================================
PROMPT 1 - select the application and find its design patterns
==================================================================================================
Role: you are a software-design reviewer helping a university team with the course
23CSE455 Design Patterns.

Case study (team A12): "Design Pattern Analysis in a Next.js-Based Video Streaming Application"
- domain: OTT / video streaming, framework: React / Next.js.
- areas to investigate: user management, video catalogue, subscription, recommendation,
  authentication, content access, caching.

Tasks
1. Find one real, open-source Next.js video-streaming application on GitHub that covers as many
   of the seven areas as possible. Report URL, stars, last commit, licence and which areas it
   covers. Pin the exact baseline commit hash you will analyse.
2. Read the source of that commit (not only file names). For every design pattern you find
   (GoF, GRASP, architectural, concurrency or framework idiom) give:
   - exact pattern name and category,
   - a meaningful instance name (e.g. "Active Profile Selection", not just "Observer"),
   - every participant role mapped to the actual class / function / module / object, with
     file path and 1-based inclusive line range (roles played by a dependency: package@version
     and file),
   - intent and evidence: the problem solved and the calls/delegation that prove the pattern.
   Count one instance per independent collaboration. If a role is combined or absent, say so;
   do not invent classes for function- or module-based code.
3. List every candidate you rejected or are uncertain about, with the file location and reason.
   A class name, comment or annotation alone is not evidence.
4. Produce the datasets exactly in the format of DP_Csestudy1.pdf:
   - patterns.csv: source_version, pattern_name, pattern_type, instance_name,
     participant_roles, source_locations, intent_and_evidence
   - Pattern_count.csv: source_version, summary (per_pattern | total_pattern_types |
     total_pattern_instances), pattern_name, count
   UTF-8, one header row, quote cells containing commas, paths relative to the team folder
   (the application source is stored in data/code/).
5. Draw one component diagram of the application architecture and one editable PlantUML class
   diagram per pattern instance.
6. Write a small script that checks every cited file:line range exists, and run it.

Output: the two CSV files, the candidate list (confirmed / rejected / uncertain with counts),
the PlantUML sources, and the totals: distinct pattern types, instances, concrete participant
classes, unique participant symbols.
